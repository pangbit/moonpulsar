# 生产者 RSS 修复验证（2026-09-26）

隔离 mock A/B 证实：旧实现的 RSS 随超时窗口内的发送量增长；改为统一完成流程和每生产者一个截止时间调度器后，保留量明显下降。

基线为 `59e3964`，修复版为本次工作区实现。两版均为 Linux x86_64 native release，进程固定一个 vCPU，mock 和生产者运行在同一进程内。每次发送 100,000 条共享的 1 KiB payload，每组最多 32 条未确认消息，目标速率 10,000 msg/s；收齐回执后再等待“超时时间 + 200 ms”。每种配置各测一次，交替版本顺序，共六次，均正常完成。

| 场景 | 修复前峰值 RSS MiB | 修复后峰值 RSS MiB |
| --- | ---: | ---: |
| 不分批，超时 1 秒 | 20.85 | 7.15 |
| 不分批，超时 10 秒 | 142.21 | 6.69 |
| batch=32，超时 10 秒 | 171.96 | 7.86 |

峰值来自 `/usr/bin/time`。逐阶段当前 RSS 来自 `/proc/self/status`，两个内核接口的读数存在小幅差异，分别保存在数据中。旧版不分批、10 秒超时场景，当前 RSS 从约 6.6 MiB 逐步增长到 142.3 MiB；等待超时窗口结束后降至 10.4 MiB，支持“已完成发送仍被超时任务暂时保留”的判断。修复版同场景发送期间稳定在约 6.9 MiB。

两个 10 秒超时场景的峰值降幅约 95%。六次运行实际速率均约 10,000 msg/s，但这是限速实验，不能据此推断最大吞吐或 P99 没有回退。batch 字节上限为 128 KiB，最长等待 1 秒，通常按 32 条凑满发送；本探针未加入性能报告的延迟直方图，因此不能把此处 RSS 与此前真实 Broker 报告直接相减。

新增 9 项回归覆盖截止时间索引删除、成功后状态归零、batch 部分/全部超时、主动关闭及 Broker 关闭清理、分块共用期限、重连保留期限，以及容量等待不计入期限。完整 native 测试 323/323 通过，类型检查通过；公开接口不变。后续已恢复真实 Broker 并执行[三方性能复测](../2026-09-26-rss-broker-rerun/README.md)，吞吐、P99、RSS 及大消息测试限制见该报告。

[脱敏数据](summary.json)仅包含配置标签、数值和验证状态。原始日志保留在报告目录之外。

复现使用 [RSS 探针](../../scripts/rss_probe_wbtest.mbt)：在两个独立检出中将同一探针临时复制到模块根目录，按文件注释构建，编译结束后串行运行。设置 `RSS_TIMEOUT_MS=1000` 或 `10000`，以及 `RSS_BATCH=0` 或 `32`。探针只连接它创建的进程内 mock，不依赖或操作已有 Broker。
