# 持续负载测试（2026-09-28，部分完成）

本批于北京时间 10:19 启动，15:32 因主机可用内存低于 2 GiB 触发保护停止。18 组速率校准通过，正式对照完成 17/18 组；最后一组 Go 64 KiB 测试约运行 601 秒后中止，不纳入结果。计划中的 2 小时 MoonPulsar 长稳测试没有开始。

**另发现采样实现缺陷：每秒采样覆盖了旧记录，每组只留下最后一条，无法计算 RSS 趋势、CPU 时间曲线或积压变化。** 本报告仅使用可验证的完整运行吞吐、整体 P99、进程峰值 RSS 和进程总 CPU 时间，不将其解读为长期稳定性证明。

## 配置与验证

使用 `8b4eeb6` 对应的 MoonPulsar RSS 修复版，以及固定版本 Go `a83c151`、Rust `929bc54` 的 Linux release 二进制。环境为 Pulsar 4.2.4 standalone，共享 Linux x86_64 主机，24 vCPU / 16 GiB；客户端与 Broker 同机。

1 KiB 依次校准 1,000 / 3,000 / 5,000 msg/s；64 KiB 依次校准 100 / 300 / 500 msg/s。每档三个客户端各预热 10 秒、测量 30 秒，全部通过，选择 5,000 和 500 msg/s 作为共同速率。这是保守候选档位，不是最大容量测量。

正式对照串行执行，每组生产者预热 2 分钟、测量 15 分钟，轮换客户端顺序。消费者提前 2 秒启动，预热多 4 秒、测量少 3 秒。32 并发，batch 最多 100 条 / 128 KiB / 1 ms，队列 1000，超时 10 秒；无 TLS、无压缩；收发进程各固定一个 vCPU，Go 单个 GOMAXPROCS，Rust 单线程 Tokio。每组先在新 Topic 上执行实际收发就绪检查。

17 组完整运行的 34 个收发进程正常退出、标准错误为空、发送延迟直方图无溢出，并验证了测量时长、就绪结果和 Topic 删除状态。校准另有 18 组、36 个正常收发退出。运行门槛为发送达到目标的 98%、消费达到目标的 95%、发送确认 P99 不高于 250 ms；全部完整运行均通过。这是本批运行门槛，不是业务 SLO。

## 中止与证据缺口

- 直接中止原因是运行器读取到主机可用内存不足 2 GiB；不是一次已确认的客户端发送错误。停止后 Broker 仍运行，主机内存后来回升，且观察到其他计算负载，但没有主机历史采样可支持进一步归因。
- 压测服务及所属收发进程已退出。35 组正常完成的校准/正式 Topic 删除返回 204；失败组清理检查返回 404，确认已不存在，不把它记录成主动删除成功。未重启 Broker、调整配置或干预其他任务。
- `@fs.write_file(..., append=true)` 仍使用默认 `CreateOrTruncate`，导致旧采样被截断。已将私有运行器写入方式改为 `create_mode=OpenOrCreate`，并在测试机验证连续三次写入全部保留；没有重新发起负载。此前“采样持续更新”只能证明采样在运行，不能证明历史已留存，这部分验证不足。
- 只有单条最终采样，无法给出 CPU 差分、RSS 斜率、持续积压趋势或采样间隔覆盖率。采样缺陷不影响独立保存的适配器结果和 GNU time 进程统计，但本批资源趋势验证失败。
- 2 小时长稳未开始。每组 P99 只有整体值；消息没有唯一序号，不能证明零丢失、零重复。没有故障注入，不能声明恢复能力。共享主机的内存压力和交换活动也限制了资源对比的解释。

后续应先验证采样文件确实累积、记录主机内存与交换指标并确认测试期间资源可控，再补测中断组和长稳测试；要取得完整时间趋势，已执行组也需要重新采样。本批已停止，未自动重跑。
