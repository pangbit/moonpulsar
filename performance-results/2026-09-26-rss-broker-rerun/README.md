# RSS 修复后的真实 Broker 性能复测（2026-09-26）

后续进展：2026-09-28 已完成[64 KiB 三方三轮对照](../2026-09-28-64k-comparison/README.md)。本文保留当日失败尝试和验证边界。

修复后的 MoonPulsar 已完成四种 1 KiB 场景的三方对照：36 组正式测试、6 组冒烟测试，纳入汇总的 84 个收发进程均正常退出，延迟直方图无溢出，专用 Topic 均清理成功。另有启动后首组冒烟消费者测量窗口无消息，已判失败并排除；换新 Topic 复试通过，失败原因未确认。

版本：MoonPulsar 为 `59e3964` 基础上的本次 RSS 修复工作区；Go 客户端 `a83c151`，Rust 客户端 `929bc54`，沿用[上一轮](../2026-09-26-comparison/README.md)的参考适配程序及构建。Linux native release 生产者构建 SHA-256：`c99f5fcb2b072d4c5548424ce2e0cb74702b71dcb553bfae310663b4a3c0e71d`。

环境与口径：Pulsar 4.2.4 standalone，共享 Linux x86_64 虚拟机，24 vCPU / 16 GiB；客户端与 Broker 同机，Token 认证，无 TLS、无压缩。每个收发进程分别固定一个 vCPU；Go 单个 GOMAXPROCS，Rust 单线程 Tokio，MoonBit native release。每场景三轮，轮换客户端顺序；生产者预热 3 秒、测量 10 秒；消费者提前 2 秒启动，预热 7 秒、测量 7 秒。队列 1000，发送超时 10 秒，batch 上限 128 KiB、等待 1 ms。

真实 Broker 结果支持 RSS 修复有效，本轮未观察到吞吐或 P99 回退。前后是不同批次的共享环境短时测量，Broker 中间重启过，不能将全部吞吐变化归因于代码。batch=100 时 Go 吞吐仍较高；batch=32 时 MoonPulsar 与 Rust 的结果接近且逐轮范围重叠，不宜宣称稳定领先。

64 KiB 连续矩阵复测中，MoonPulsar 首轮成功，随后 Go 首轮期间 Broker 再次达到 4 GiB 堆外内存上限并退出。此轮大消息结果不纳入排名，不能据此认定 Go 客户端缺陷。

随后尝试每组重启 Broker：Go 首轮生产成功，但消费窗口无消息。再为所有客户端统一增加窗口外预热（相同 64 KiB 消息，100 msg/s、1 秒），Go、Rust 首轮收发成功，MoonPulsar 首轮生产成功但消费窗口仍无消息。收发进程耗时证实窗口重叠；Broker 同时记录该测试 Topic 的事务缓冲快照恢复超时并关闭 Topic。HTTP 健康检查通过并不代表此时该 Topic 的消费链路就绪。隔离尝试也未形成完整三轮对照，全部排除出汇总。

因此，64 KiB 三方复测仍未完成。需要先解决 Broker 堆外内存和事务快照恢复问题，再以端到端收发探针确认就绪后重测。以上失败期间产生的专用测试 Topic 已清理；未调整 Broker 内存、事务配置或清理其他数据。

本地 21 项微基准已重新执行并全部通过（3 个 benchmark 测试块）；它们在开发机执行，不与上述 Linux Broker 数值混合。此次未改动客户端代码，沿用修复完成时 323/323 native 回归通过的证据。

这些测试不代表长期稳定性或生产容量。消费者受供给限制，收发窗口不同，不能由计数差推算丢失率；发送确认 P99 不是端到端延迟。Rust 的适配层等待超时不等同于库内部 operation timeout。
